# Deploying OushodhSathi

Two pieces: the FastAPI backend on **Render** and the Next.js frontend on **Vercel**.
Both deploy from this GitHub repository. No secret is ever committed; every key is
entered in the provider's dashboard.

## 1. Backend → Render

1. Render dashboard → **New → Blueprint** → choose this repository. Render reads
   [`render.yaml`](../render.yaml) and proposes one web service, `oushodhsathi-api`.
2. Fill in the variables marked *sync: false* when Render asks for them:

   | Name | Required | What to put |
   | --- | --- | --- |
   | `CORS_ORIGINS` | yes | Your Vercel URL, e.g. `https://oushodhsathi.vercel.app` |
   | `CORS_ORIGIN_REGEX` | no | `^https://oushodhsathi-.*\.vercel\.app$` to allow preview deploys |
   | `DATABASE_URL` | for data that survives restarts | Supabase session-pooler URL, see **Database** below |
   | `NVIDIA_API_KEY`, `NVIDIA_MODEL`, `NVIDIA_VISION_MODEL` | no | First provider in the AI chain when set |
   | `OPENROUTER_API_KEY` | for live scans | Your OpenRouter key |
   | `OPENROUTER_VISION_MODEL`, `OPENROUTER_TEXT_MODEL` | no | Blank = auto-pick a free model |
   | `TAVILY_API_KEY`, `PERPLEXITY_API_KEY` | no | Unknown-brand web lookup |
   | `N8N_ALERT_WEBHOOK` | no | n8n webhook for red-flag doctor alerts |

   `REVIEWER_TOKEN` is generated by Render. Open the service → **Environment** to read
   it; that is the token reviewers type on `/review`.
3. Deploy. The blueprint uses Render's **free** plan, which has no disk: without
   `DATABASE_URL` the API uses a local SQLite file that resets whenever the instance
   restarts. Free instances also sleep after ~15 idle minutes; the first request then
   takes up to a minute. On start, `scripts/seed_demo.py --if-empty` creates the invented
   demo household only when the database is empty.
4. Check `https://<service>.onrender.com/health` returns `"status": "ok"`.

### Database (free Supabase Postgres)

1. Supabase → new project, region **Southeast Asia (Singapore)**.
2. SQL editor: give the API its own login and a private schema. Only `public` is
   exposed through Supabase's REST API, so the API's tables are not reachable with the
   public anon key:

   ```sql
   create schema if not exists oushodh;
   create role oushodh_app login password '<long random password>';
   grant usage, create on schema oushodh to oushodh_app;
   alter role oushodh_app set search_path = oushodh;
   ```
3. Set `DATABASE_URL` on Render to the **session pooler** (Render's free plan has no IPv6,
   and the direct `db.<ref>.supabase.co` host is IPv6-only):
   `postgresql://oushodh_app.<ref>:<password>@aws-0-ap-southeast-1.pooler.supabase.com:5432/postgres?sslmode=require`
4. The API creates its tables on first start. A free Supabase project **pauses after
   about 7 days without activity**; resume it from the Supabase dashboard (one click),
   and data is kept.

### Abuse limits

Rate limits are kept in memory per client IP (first `X-Forwarded-For` entry), which is
enough for the single free instance; they reset on restart. Defaults: 10 scans per IP per
hour, 200 scans per day overall, 5 new households per IP per hour, 120 writes per IP per
hour. Over the limit the API answers `429`.

### Private family links

Every household except the invented demo gets a random family key when it is created.
Family pages send it as `X-Family-Key`; without it (or a reviewer token) the API answers
`404`, so household ids cannot be probed. The family shares access with **Share with
family** on the household home, which sends `/p/<id>?key=…`. Reviewers can list every
household and its key with `GET /patients`. The n8n report workflows read
`OUSHODH_FAMILY_KEY` alongside `OUSHODH_PATIENT_ID`.

Ollama does not run on Render (`OLLAMA_DISABLED=1`), so hosted Bangla explanations use
the cloud fallback, then the fixed templates. Run locally for private explanations.

`DEMO_MODE=true` lets the scan flow work without any keys (it returns the demo shelf).
Set it to `false` once a vision key is configured.

## 2. Frontend → Vercel

1. Vercel → **Add New → Project** → import this repository.
2. **Root Directory**: `frontend`. Framework preset: Next.js (auto-detected).
3. Environment variable: `NEXT_PUBLIC_API_URL` = `https://<service>.onrender.com`.
4. Deploy, then put the Vercel URL into Render's `CORS_ORIGINS` and redeploy the API.

## 3. Smoke test

- `/` landing → **See the demo** → step through `/demo`.
- `/start` → add a household → add two medicines with times → send for review.
- Open that household's address in a private window without `?key=`: "not found".
- `/review` → sign in with the Render `REVIEWER_TOKEN` → confirm a flag with a note.
- `/p/1/results` now shows the confirmed flag with its Bangla explanation.
- `/passport/1` → browser print preview (A5).

## 4. Secrets hygiene

Before every release, search the history for key prefixes:

```
git log --all -p | grep -nE "sk-[A-Za-z0-9_-]{10,}|pplx-|tvly-[A-Za-z0-9]|xpl_"
```

Last checked on the `prototype` branch: no real keys found (one fake test value,
`tvly-secret-value`, in `backend/tests`). Keys pasted into any chat must be rotated
regardless.
